# 04｜本地测试：不上测试网，怎样先检查合约？

## 这一篇要解决的问题

前三节沿着 `Ping → react() → 回调` 走了一遍。这节看仓库怎样用本地测试检查其中的逻辑，以及测试通过能说明什么。

## 正文

### 1. 我们要验证什么？

先选一个具体问题：当事件携带的数字是 `500`、阈值为 `100` 时，回调接收合约是否最终记录了 `500`？

真实测试网需要部署合约、准备测试币，并等待 Reactive 网络投递。本地测试在电脑上的测试环境中创建合约，并使用模拟组件代替部分网络基础设施，以便检查程序行为。

这就像先在练习环境里检查关键动作。练习环境的结果可以帮助找代码问题；真实网络上的部署、通信、余额和投递，仍要在实际测试网另行验证。

### 2. 项目里谁负责测试？

打开 [Camp.t.sol](../../starter/test/Camp.t.sol)。这是项目作者写的测试文件，其中有多段以 `test_` 开头的函数，每一段检查一个场景。

例如：

- `test_originEmitsPing`：检查调用源合约后是否产生预期的 `Ping` 事件。
- `test_belowThresholdNoCallback`：检查低于门槛时是否没有回调请求。
- `test_fullLoop_eventToCallback`：检查模拟事件输入后，回调接收合约能否记录结果。
- `test_callbackRejectsWrongProxy`：检查直接调用、调用者不是指定 Proxy 时是否被拒绝。

这些名字是作者对测试起的名字；真正验证了什么，需要看测试里面实际做了什么。

### 3. 用一个测试看完整过程

在同一文件中搜索 `function test_fullLoop_eventToCallback`。这段测试可以翻译成：

```text
测试代码准备一条模拟事件记录，里面的数字是 500
    ↓
以模拟系统的身份调用 CampReactive.react()
    ↓
检查模拟系统是否收到了一个回调请求
    ↓
测试代码让模拟 Proxy 投递这次请求
    ↓
检查 CampCallback 的 count 是 1，lastValue 是 500
```

这里有个值得注意的细节：**这个测试函数没有先调用 `CampOrigin.ping(500)`，也没有让真实 Reactive 网络自动发现事件。** 它直接构造一条模拟事件记录，然后由测试代码调用 `react()` 和模拟 Proxy。源合约是否发出事件由另一个 `test_originEmitsPing` 分别检查。

这样可以检查多个关键环节，但本地的模拟过程和真实跨链投递不是同一回事。

### 4. 模拟组件是什么？

同一个测试文件里有两个名字以 `Mock` 开头的合约。`Mock` 在这里表示为测试准备的模拟组件：

| 模拟组件 | 在这个测试中的作用 |
|---|---|
| `MockSystem` | 接收并记录订阅、退订和回调请求，方便测试检查 |
| `MockProxy` | 模拟 Proxy 投递回调并注入 Reactive 合约地址 |

它们只实现了测试需要的部分行为。真实 Reactive 系统和目标链上的 Proxy 还有自己的运行、投递和收费过程。

### 5. 谁运行这些测试？

项目使用 **Foundry**，它是一套智能合约开发工具；其中 `forge` 可以编译合约、运行测试。仓库 README 给出的测试命令是：

```powershell
forge test -vv
```

它要在 `starter` 目录下运行。`-vv` 控制输出的详细程度。这个仓库已经在本机，所以无需再次执行 README 中的 `git clone`。

2026 年 11 月 13 日，我在当前 PowerShell 环境中检查时，`forge` 没有出现在可执行命令路径中；这不足以证明电脑上任何位置都没安装，也没有实际运行测试。**项目 README 写的 8 个测试通过，是作者提供的记录，不是我们这台电脑本次测试的结果。**

本地测试阶段不需要测试钱包私钥或测试币；首次安装工具、依赖或编译器时可能需要联网。等你准备动手，我们可以先确认 Windows 上 Foundry 的安装状态，再处理实际出现的问题。

### 6. 如何理解测试结果？

假设之后运行时看到某个测试 `PASS`：它说明该次运行中，测试代码写下的检查都通过了。例如，上面的完整流程测试检查了 `count` 和 `lastValue`。

它无法单独证明真实 Sepolia 与 Lasna 的 RPC、Proxy 地址、资金和网络投递都正常。真实测试网验证需要另外部署并查询交易记录。

## 小结

- 测试文件预先写好一系列场景和检查，Foundry 的 `forge` 负责运行。
- 本例使用 `MockSystem` 和 `MockProxy` 替代部分真实基础设施。
- 完整流程测试从模拟事件记录开始；源合约发事件由另一项测试单独检查。
- 本地测试通过说明对应检查通过，真实测试网结果要另外验证。
